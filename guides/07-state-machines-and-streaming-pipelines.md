## 1. Override Hierarchy: Manual Overrides vs Automated State Generation

### The Architectural Conflict
In enterprise platforms (pricing engines, automated scheduling, logistics dispatch, resource allocation), operational state can be generated automatically by an **Automated State Generator** or entered manually by an authorized human operator.

When a query requests the effective state for an Resource At a given time:
- An automated rule exists (generated by a recurring template: e.g. "Default Capacity = 100").
- A human operator entered a manual exception (e.g. "Override Capacity = 40 due to maintenance").

### The Invariant: Manual Always Overrides Automated
**Rule**: Manual human overrides strictly take precedence over automated state generators.
The resolution pipeline must:
1. Load all manual overrides first into an index keyed by `resourceID`.
2. Evaluate automated state rules.
3. For each automated result, if the `resourceID` exists in the manual override index, **discard the automated result**.
4. Tag each item in the API response with its origin: `source: "MANUAL"` or `source: "AUTOMATED"`.

```go
func MergeStates(manuals []ResourceState, automated []ResourceState) []ResourceState {
	manualIndex := make(map[string]bool, len(manuals))
	for _, m := range manuals {
		manualIndex[m.ResourceID] = true
	}

	merged := make([]ResourceState, 0, len(manuals)+len(automated))
	// 1. Manual always wins
	for _, m := range manuals {
		m.Source = "MANUAL"
		merged = append(merged, m)
	}

	// 2. Add automated state only if no manual override exists
	for _, a := range automated {
		if manualIndex[a.ResourceID] {
			continue // Suppressed by manual override
		}
		a.Source = "AUTOMATED"
		merged = append(merged, a)
	}
	return merged
}
```

## 2. Multi-Stage State Lifecycles: Draft $\rightarrow$ Staged $\rightarrow$ Live

### The State Lifecycle
Complex operational states evolve through three distinct phases:

```
┌─────────────────────────────────────────────────────────────┐
│                           DRAFT                             │
│  Proposed / Working state. Always generated when rules are  │
│  active. Visible only to planners and staging environments. │
└──────────────────────────────┬──────────────────────────────┘
                               │ Commit / Publish Action
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                          STAGED                             │
│  Committed target state. Governs downstream reservations,   │
│  staffing, and external visibility for confirmed windows.   │
└──────────────────────────────┬──────────────────────────────┘
                               │ Real-Time Execution Horizon
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                           LIVE                              │
│  Real-time operational execution. Bounded to current        │
│  active horizon (e.g. Today and Tomorrow).                  │
└─────────────────────────────────────────────────────────────┘
```

### Key Architectural Lessons:
1. **Shared Underlying Definitions**: Draft and Staged states often share the **same rule definition**. The difference is the gate criteria:
   - Draft is generated unconditionally for all future targets within the rule's active date range.
   - Staged is only generated for explicit date ranges that have been approved or published.
2. **Live States Have Independent Bounds**: Live operational states require strict time horizons (e.g. limited to `CurrentTime` and `CurrentTime + 24h`) and must never calculate arbitrarily far into the future without live telemetry.
3. **Dependency Chaining**: When a Live state derives its baseline from Staged state (e.g. applying real-time offsets to approved plans), pre-fetching must ensure Staged dependencies are resolved first.

## 3. Cache Lifecycle: Active, Deprecated, and Definitive States

### The Cache State Architecture
Automated state calculations are computationally expensive to recompute from raw rules on every request. They are cached in storage:

| State | Flag | Purpose |
|---|---|---|
| **Active** | `deprecated: false` | Served immediately on API read queries (`cache hit`). |
| **Deprecated** | `deprecated: true` | Invalidated by an upstream change. Preserved for historical audit and delta reconciliation. |
| **Definitive** | `definitive: true` | Locked state (e.g. finalized past business day). **Never deprecated or recalculated.** |

### Invalidation & On-Demand Fallback:
1. An operator modifies a rule $\rightarrow$ A background worker marks affected cache records as `deprecated: true` $\rightarrow$ publishes invalidation event to a stream.
2. An asynchronous generator consumes the event $\rightarrow$ recalculates state $\rightarrow$ writes new active cache (`deprecated: false`).
3. **On-Demand Fallback**: If a read request arrives before the background generator completes, the reader detects a cache miss, generates the state synchronously, updates the cache, and responds.

## 4. Multi-Stage Streaming Pipelines for Heavy Endpoints

### The Failure Mode
An administrative endpoint (`GET /v1/resources/export`) fetches complex state for 500 resources.
The naive sequential code:
1. Fetches all 500 resource IDs.
2. Loops through each resource, fetching its data sequentially over HTTP ($500 \times 100\text{ms} = 50\text{s}$).
3. Filters and transforms the records in memory.
4. Serializes the massive array.
**Result**: 504 Gateway Timeout and high memory usage.

### Recommended Pattern: 4-Stage Streaming Concurrent Pipeline
Transform the batch loop into a pipelined worker model using channels:

```
[Stage 1: Producer]       [Stage 2: Parallel Workers]       [Stage 3: Transformer]       [Stage 4: Collector]
Fetch resource IDs   ───►   Fetch State (10 Workers)    ───► Filter & Clean Records ───►  Aggregate Final Output
```

```go
package pipeline

import (
	"context"
	"sync"
)

func ExecuteStreamingPipeline[In any, Out any](
	ctx context.Context,
	items []In,
	concurrency int,
	workerFn func(ctx context.Context, item In) (Out, bool),
) []Out {
	inChan := make(chan In, len(items))
	outChan := make(chan Out, len(items))

	// Feed items into input channel
	for _, item := range items {
		inChan <- item
	}
	close(inChan)

	// Spawn bounded worker pool
	var wg sync.WaitGroup
	for i := 0; i < concurrency; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for item := range inChan {
				select {
				case <-ctx.Done():
					return
				default:
					if res, ok := workerFn(ctx, item); ok {
						outChan <- res
					}
				}
			}
		}()
	}

	// Close output channel once all workers finish
	go func() {
		wg.Wait()
		close(outChan)
	}()

	// Collect results
	var results []Out
	for res := range outChan {
		results = append(results, res)
	}
	return results
}
```
